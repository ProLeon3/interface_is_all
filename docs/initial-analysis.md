## 已实现的使用流程

选择根目录含 `go.mod`、没有有效确认设计的项目后，在代码起草方式中点击「分析已有代码」，无需预先建立模块或接口。已有草稿时先展开「调整设计」，再选择代码分析。打开目录仅读取状态，不会扫描、生成草稿或确认版本。已有草稿可以作为分组参考，但模型必须依据实际代码还原现状。

分析返回现状设计提案，沿用已有图形对照、继续调整、接受到草稿、手动编辑及完整版本确认。接口或模块详情可以展开相应的原始源码；图下单独展示读取范围、问题、改进建议与不确定项。接受只保存草稿，确认才建立检查基准（「接受并审阅确认」把两步连起来做）；之后使用原来的依赖检查和能力审查流程。

提案及分析来源保存在项目中，另一浏览器窗口也能恢复待审阅分析。接受后手动修改设计不会改写原始分析证据。确认表示用户选择设计作为约束，不等于认可现有架构、业务正确或模型没有遗漏。

## 源码、范围与模型上下文

[source](../source/scan.go) 从原检查包抽出共同的事实采集能力；[check](../check/scan.go) 保留原公开接口、JSON 事实形状和确定性判定行为。无设计扫描仍保留包依赖，不把模块归属缺失误当成没有依赖。

首次分析通过 `source.Collect` 采集根目录的单个 Go module，遵守当前 GOOS、GOARCH、CGO、工具链和显式构建标签。纳入构建的 Go 文件保留完整内容及私有辅助逻辑，公开声明只作为候选线索。源码以包路径、项目相对路径和物理行号组织；模型看到包清单、已读文件、包内排除文件、依赖、构建清单及范围。测试、其他构建条件、嵌套 module、vendor、隐藏目录、下划线目录和 testdata 不纳入源码分析；嵌套 module 会产生不完整诊断。

首版采用完整上下文，序列化的源码上下文上限为 **1 MiB**。不静默抽样、切断函数或省略超限文件。加载有诊断、没有可读源码或超限时，不调用模型、不生成提案；页面展示实际范围和原因。底层命令无法启动或依赖清单无法读取时直接报告失败。模型服务自身的上下文上限可能更小，服务拒绝时保留原草稿，不自动重试。

`source.fingerprint` 对源码内容、包清单、排除清单、公开候选、包依赖、构建清单和构建条件生成 SHA-256。生成完成、接受以及首次确认都会重新扫描比较。新增或删除纳入范围的文件、修改源码或依赖清单、改变实际构建条件都会使旧结果失效。范围外的测试内容不作为本次语义结论依据。

[源码分析指令](agent-prompts/source-analysis.md) 与普通需求设计指令分开。普通需求请求保持原形状；初次分析及其继续调整增加 `source`，输出增加 `analysis`。实施当时由内置模型客户端发送请求；迁移后同样的请求与响应形状改由外部 agent 通过文件交换。

## 分析依据与建议的边界

[校验器](../designer/analysis.go) 要求每个模块、接口和协作都有且仅有一个依据项，说明结论、状态及源码位置。不存在的文件、越界行号、错误的对象引用、缺少所属模块依据、没有已读源码的模块目录、遗漏已扫描包都会被拒绝。初次分析的 `forbidden_dependencies` 必须为空，旧草稿中已有的规则也不被自动复制为代码现状。

模块和接口的 `supported` 表示模型提供了可定位的依据，页面标为「有源码依据 · 待核对」，不代表程序完成语义证明。若模型只在协作条目提供调用方位置，客户端会从它明确引用的接口中复用目标源码证据；不会生成新的文件或行号，已有但错误的目标位置仍会被拒绝。协作还有额外限制：[直接使用校验](../designer/analysis_usage.go) 核对调用方证据中的包成员引用，并要求接口依据与协作目标依据落在同一公开声明。只有包导入、无关函数或无关目标声明都不能形成 `supported` 协作。方法接收者、注入、点导入、反射及其他无法静态关联的情况，保留为 `uncertain`，需要用户审阅。

`analysis.issues`、`analysis.suggestions` 与 `analysis.uncertainties` 分开保存、显示，不自动改变设计。建议只有在用户接受后主动编辑设计时才可能成为目标约束。源码引用校验仍不能证明自然语言职责描述正确，不能取代实际源码核对。

原设计约束仍要求模块目录互不重叠。如果根目录本身含源码，模型可能需要使用一个根模块覆盖项目；不得为了画出更理想的分层虚构目录。相关表达限制应记为不确定项。

## 存储与并发保护

| 数据或接口 | 行为 |
| --- | --- |
| `POST /api/initial-analysis` | 提交读取时的草稿指纹和空基准版本；扫描、生成、验证并保存待审阅提案 |
| `GET /api/state` | 校验草稿与确认快照后给出首次入口状态和已保存的分析引用；不是依据目录或报告是否存在判断 |
| `POST /api/proposals` | 若父提案含源码，继续携带同一源码快照和分析协议进行调整 |
| `POST /api/proposals/{id}/accept` | 同时复核源码、草稿、确认版本和当前分析引用，只写草稿 |
| `POST /api/initial-analysis/discard` | 明确撤回分析，保留草稿及不可变提案；已有基准不允许重置首次接入 |
| `.architecture/proposals/<id>.json` | 内容哈希保护的提案，包含完整输入源码、原草稿、结果和单独分析依据 |
| `.architecture/initial-analysis.json` | 记录待审阅、接受中、已接受或已撤回状态，支持跨窗口恢复 |
| 确认快照的 `initial_analysis_id` | 可选的永久来源引用；旧快照没有该字段时指纹保持兼容 |

生成结束后在存储锁内再次检查版本。生成期间另一窗口保存草稿或建立了基准，旧结果不能发布。草稿读取失败、损坏确认 JSON、确认历史缺失或分析引用损坏均按错误处理，不降级为未分析状态。项目路径始终随请求固定，提案只能从所在项目读取和接受。

接受涉及草稿和来源状态两个文件，因此先持久写入 `Accepting`，再写草稿，最后写入 `Accepted`。进程在中途退出时，同一份草稿可以幂等补全接受；其他编辑仍冲突。接受中或已接受的来源被撤回时转为 `Withdrawn`，首次确认继续拒绝旧草稿，直到新分析被接受。未曾接受的普通待审阅提案撤回不影响原有手写草稿。

浏览器保留未保存编辑保护，生成期间不能切换项目。冲突时可以明确撤回旧分析，撤回操作读取当前版本且只改变来源记录，不覆盖草稿。重新分析期间，旧证据保留；失败范围优先展示，不让旧记录遮住本次读取问题。

## 真实模型核对

用户明确授权后，仅将 `examples/shop` 副本中的 `order/cancel.go`、`payment/api/refund.go` 和 `go.mod`，连同它们的扫描事实，发送到 `.env.archdesign` 配置的模型服务。使用 `responses` 协议、`gpt-5.6-sol` 模型及 `xhigh` 推理配置；原项目和示例文件均未因此改写。

前两次请求因协作条目只列调用方、没有重复列出目标源码而被拒绝，没有生成可接受提案。模型已经在对应接口条目提供了目标源码，因此补充前述确定性证据复用后，再次调用成功。验收保存了[补全前的模型结构化输出](verification/initial-analysis/real-model-result.json)和[浏览器验收记录](verification/initial-analysis/real-journey.json)，两者可对照查看；没有保存凭据、模型服务地址或本地会话令牌。

本次逐项对照实际示例源码，结论如下：

## 提示词复测与消息传递修复

2026-09-21 根据用户要求，对上节提示词修正进行真实复测。继续仅发送已授权的三文件示例副本，模型和推理配置保持 `gpt-5.6-sol` / `responses` / `xhigh`，源码指纹与前次相同。发送前核对实际请求体，确认修正规则确实发出；修正后的提示词 SHA-256 为 `142d17ba278a920ed6b387235507b84ef7fd657058bd2a5e9d2e4b1c9bd8cd9e`。

仅修改提示词的第一轮仍然失败：模型继续把空 `module_id`、`unassigned_packages` 列为问题，并建议补包到模块的映射。该问题的 `locations` 为空，程序拒绝整个提案，没有保存草稿或确认版本。见[失败原始输出与请求核对记录](verification/initial-analysis/prompt-retest-instructions.json)。

这一轮服务响应中的 `instructions` 与客户端发出的内容不同，也没有修正规则。这是兼容服务可能改写顶层指令的线索；没有检查服务内部实现，不能仅据此确定模型的最终上下文。

根据 OpenAI Docs 的[消息角色说明](https://developers.openai.com/api/docs/guides/text#message-roles-and-instruction-following)，Responses 支持通过 `input` 中的 `developer` 消息传递应用规则。[客户端](../designer/designer.go)现将相同提示词和 Schema 放入该消息，完整需求及源码 JSON 仍放在独立 `user` 消息。Chat Completions 的格式保持原状；没有放松输出校验或过滤掉模型的误报。
